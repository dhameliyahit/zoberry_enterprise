PHASE 1 — ZOBERRY PRODUCTION FOUNDATION
========================================

ROLE:
You are working on the existing Zoberry e-commerce application.

STACK:
- Frontend: React
- Backend: Node.js + Express
- API: GraphQL / Apollo
- Database: MySQL + Sequelize
- SSR is already part of the application.
- Do NOT replace the existing stack.

GOAL:
Prepare the existing Zoberry codebase for a real production e-commerce business.

This is NOT a demo.
This is NOT a UI-only task.
This is NOT a Shopify clone.

We want the technical foundation required for a serious Shopify-like customer experience later.

IMPORTANT:
Do not blindly follow a generic architecture.
Inspect the existing code first and preserve anything that already works correctly.

The current audit shows:
- Express 5.2.1
- Apollo Server 5.5.1
- Sequelize 6.37.8
- MySQL
- JWT authentication
- User, Category and Product models already exist
- CartItem and WishlistItem exist but are currently unused
- Order, OrderItem, Address, Payment, Coupon, Review and Inventory models do not yet exist
- Several admin/user mutations are currently unprotected
- Product listing is currently unpaginated
- Image upload endpoints are currently unauthenticated
- JWT has no configured expiration
- sequelize.sync({ alter: true }) is currently used at startup

PHASE 1 SCOPE:
ONLY foundation, security, data integrity and architecture preparation.

DO NOT IMPLEMENT:
- PhonePe
- courier/logistics API
- payment gateway
- shipping provider
- coupon UI
- reviews UI
- wishlist UI
- advanced frontend redesign
- marketing automation
- unnecessary microservices
- Redis/BullMQ unless the existing code genuinely requires it

Those belong to later phases.

--------------------------------------------------
2. FIX AUTHENTICATION
--------------------------------------------------

Make authentication production-safe.

Requirements:

- Validate Authorization header correctly.
- Reject malformed Bearer tokens safely.
- Add JWT expiration.
- Never expose JWT secrets.
- Never return password hashes.
- Validate email properly.
- Validate password requirements.
- Prevent blank/null passwords.
- Handle duplicate email registration safely.
- Handle Google authentication safely.
- Do not trust client-provided user IDs.
- Current authenticated user must come from verified authentication context.

Do not break existing login/register functionality.

--------------------------------------------------
3. IMPLEMENT REAL AUTHORIZATION
--------------------------------------------------

Create clear authorization helpers/middleware such as:

requireAuth()
requireAdmin()

Rules:

CUSTOMER:
- Can access own account.
- Can modify own profile where allowed.
- Can later access own cart/orders/wishlist.

ADMIN:
- Can manage products.
- Can manage categories.
- Can manage users where appropriate.
- Can access administrative operations.

PUBLIC:
- Can browse active categories.
- Can browse active products.
- Can view product details.

CRITICAL:

A client must NEVER be able to supply another user's ID and modify/delete that user's data.

Protect every mutation according to ownership/role.

Specifically audit and secure:

- getUserById
- getAllUsers
- updateUser
- deleteUser
- createCategory
- updateCategory
- deleteCategory
- createProduct
- updateProduct
- deleteProduct

Do not simply hide these operations from the frontend.
The backend must enforce authorization.

--------------------------------------------------
4. FIX DATABASE SAFETY
--------------------------------------------------

The application currently uses:

sequelize.sync({ alter: true })

Do NOT leave production database startup dependent on automatic schema alteration.

Introduce a safer migration strategy appropriate for this existing Sequelize application.

Requirements:

- Existing data must be preserved.
- Do not drop tables.
- Do not reset the database.
- Do not delete existing products/users/categories.
- Do not perform destructive migration automatically.
- Make development and production behavior clearly separated.

Before executing migrations, inspect the current schema.

--------------------------------------------------
5. IMPROVE CURRENT PRODUCT DATA FOUNDATION
--------------------------------------------------

Do NOT redesign the entire product model yet.

Improve the existing Product model only where necessary for production readiness.

Ensure:

- price cannot be negative
- stockQuantity cannot be negative
- product name is required
- slug is required and unique
- category relationship is valid
- inactive products are not accidentally exposed as purchasable products

Add appropriate database indexes for common storefront queries.

At minimum evaluate indexes for:

- categoryId
- isActive
- slug

Do not blindly add indexes without considering actual queries.

--------------------------------------------------
6. FIX PRODUCT QUERY SCALABILITY
--------------------------------------------------

The current getAllProducts query loads all products.

Replace this with proper server-side pagination.

The API should support concepts such as:

- page
- limit
- category
- active status
- search
- sorting

Do not load thousands of products into memory just to paginate on the frontend.

Return:

items
total
page
limit
totalPages

Keep the API design reusable for future category/search pages.

--------------------------------------------------
7. SECURE IMAGE UPLOADS
--------------------------------------------------

Current upload endpoints are publicly accessible.

Secure administrative uploads.

Requirements:

- admin authentication
- MIME validation
- extension validation
- file size limit
- sensible image dimensions
- safe filenames
- WebP processing where appropriate
- reject unsupported file types
- prevent arbitrary file uploads
- prevent uncontrolled memory/disk consumption

Do not break existing product image functionality.

--------------------------------------------------
8. ERROR HANDLING
--------------------------------------------------

Introduce consistent backend error handling.

Do not expose:

- SQL errors
- stack traces
- internal filesystem paths
- JWT internals
- database structure
- sensitive implementation details

to normal customers.

Create consistent API/GraphQL errors suitable for frontend handling.

Log detailed errors server-side.

--------------------------------------------------
9. VALIDATION
--------------------------------------------------

Every important mutation must validate input.

Examples:

Product:
- name
- slug
- price
- stock
- category

Category:
- name
- slug

User:
- email
- password
- profile fields

Reject invalid input before database operations.

Do not rely only on frontend validation.

--------------------------------------------------
10. DATA OWNERSHIP RULES
--------------------------------------------------

Establish a strict rule:

NEVER trust IDs supplied by the browser for authorization.

For customer-owned resources:

1. Authenticate the user.
2. Determine the authenticated user from the server-side auth context.
3. Query the resource using that authenticated user.
4. Only then perform the operation.

This foundation is critical because future features will include:

- cart
- wishlist
- addresses
- orders
- payments
- returns
- reviews
