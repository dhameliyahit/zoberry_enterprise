==================================================
STEP 2 — MONEY MODEL MUST BE CORRECT
==================================================

This is extremely important.

Do NOT use JavaScript/SQL floating-point values as the authoritative source for order financial calculations.

Review the existing Product price fields.

Choose ONE robust strategy and apply it consistently.

Preferred approach:

Store monetary values using DECIMAL in the database.

For example:
- price
- compareAtPrice
- costPrice
- subtotal
- discountAmount
- shippingAmount
- taxAmount
- grandTotal

Do not calculate authoritative order totals using binary floating-point arithmetic.

Create a centralized money/totals utility so the same rules are used by:
- cart
- checkout
- order
- future discounts
- future payment integration

Do not scatter price calculations throughout resolvers/components.

Document the chosen approach.

Products may eventually have variants such as:

Size:
- S
- M
- L

Color:
- Black
- White

Storage:

Preferred conceptual structure:

Product
  └── ProductVariant
        ├── SKU
        ├── price
        ├── compareAtPrice
        ├── stockQuantity
        ├── option values
        └── active status

Create the minimum clean data model required.

Each variant should have:
- unique ID
- product ID
- SKU
- price
- optional compareAtPrice
- stockQuantity
- isActive
- timestamps

Create a generic option/value representation if required.

IMPORTANT:

Do not over-engineer a Shopify clone.

The architecture only needs to support real Zoberry requirements.

A product with no variants should still be easy to sell.

A product with variants should allow CartItem to reference the exact variant.

Do not break existing products.

If migration requires creating a default variant for existing products, do so safely and document it.

STEP 4 — REAL CART ARCHITECTURE
==================================================

Implement:

Cart
CartItem

Cart should support:

- logged-in customer
- guest customer/session
- active cart
- cart lifecycle
- currency
- timestamps

CartItem should support:

- cartId
- productId
- variantId when applicable
- quantity
- current/reference pricing needed for cart calculation
- timestamps

Use proper database constraints.

A cart must NOT contain duplicate rows for the same sellable item.

For example:

same product + same variant
=> increase quantity

different variant
=> separate cart item

If no variant exists:
product itself is the sellable item.

==================================================
STEP 5 — GUEST CART
==================================================

Guest users must be able to:

1. Open website
2. Add product
3. Refresh browser
4. Keep cart
5. Add more products
6. Login/register
7. Merge guest cart into their customer cart

Do not force account creation merely to add an item to cart.

Use a secure guest cart/session identifier.

Do not trust arbitrary user IDs from the frontend.

Do not put sensitive information in the guest identifier.

When guest cart merges with authenticated user's cart:

- same product/variant => quantities merge
- different items => remain separate
- unavailable/deleted products => handle safely
- inactive variants => handle safely
- quantity must respect available stock

The merge must be transactional.

==================================================
STEP 6 — CART BUSINESS RULES
==================================================

Implement server-side cart operations:

- get cart
- add item
- update quantity
- remove item
- clear cart
- merge guest cart

Validation:

- quantity must be integer
- quantity >= 1 when adding/updating
- product must exist
- product must be active
- variant must exist when supplied
- variant must belong to product
- variant must be active
- quantity cannot exceed available stock

IMPORTANT:

Never trust price sent by the browser.

The server must calculate price from the database.

Frontend is NEVER authoritative for:
- price
- stock
- discount
- subtotal
- total

==================================================
STEP 7 — INVENTORY FOUNDATION
==================================================

Do not simply decrement stock from frontend requests.

Create a proper inventory foundation.

At minimum introduce:

Inventory/StockMovement concept.

Track important inventory changes such as:

- initial stock
- manual adjustment
- order reservation
- order cancellation
- order completion/shipping if appropriate
- restock

Choose the cleanest model for the current architecture.

Every stock-changing operation must happen server-side.

Prevent negative inventory.

Handle concurrent requests safely.

Example:

Stock = 1

Two customers simultaneously try to buy quantity 1.

The system must NOT allow both orders to successfully consume the same stock.

Use database transactions and row locking / atomic update strategy appropriate for MySQL + Sequelize.

Document the chosen concurrency strategy.

- city

STEP 9 — ORDER MODEL
==================================================

Create:

Order
OrderItem

Order must represent an immutable commercial transaction.

Suggested order fields:

- id
- orderNumber
- userId nullable only if guest checkout is intentionally supported
- status
- paymentStatus
- fulfillment/shipping status
- currency
- subtotal
- discountAmount
- shippingAmount
- taxAmount
- grandTotal
- shipping address snapshot
- billing address snapshot if applicable
- timestamps

OrderItem should contain an immutable snapshot of the purchased item:

- productId
- variantId if applicable
- product name snapshot
- SKU snapshot
- quantity
- unit price
- discount amount if applicable
- line total
- product metadata required for historical display

IMPORTANT:

Do NOT depend on the current Product record to reconstruct an old order.

If the product name changes tomorrow, yesterday's order must still show the original purchased name.

If price changes tomorrow, old orders must retain their original price.

STEP 10 — ORDER NUMBER
==================================================

Create a human-friendly unique order number.

ZB-20261007-XXXXXX

Order number must be unique.

Avoid race conditions when generating it.

==================================================
STEP 11 — ORDER STATE MACHINE
==================================================

Implement explicit state transitions.

At minimum:

PENDING
CONFIRMED
PROCESSING
SHIPPED
DELIVERED
CANCELLED

You may include additional states only if genuinely necessary.

Payment state should be separate from fulfillment/order state.

For example:

Payment:
- PENDING
- PAID
- FAILED
- REFUNDED

Do NOT mix payment status with shipping/order status.

Prevent invalid transitions.

For example:

DELIVERED -> PENDING

must not be allowed.

CANCELLED -> SHIPPED

must not be allowed.

Create centralized transition rules.

Do not scatter status checks across random resolvers.

STEP 12 — CHECKOUT FOUNDATION
==================================================

Implement a server-side checkout/order creation workflow.

Conceptually:

Cart
 ↓
Validate cart
 ↓
Validate products/variants
 ↓
Validate stock
 ↓
Resolve current prices
 ↓
Resolve address
 ↓
Calculate totals
 ↓
Create Order + OrderItems
 ↓
Reserve/decrement stock according to chosen inventory strategy
 ↓
Clear/lock cart appropriately
 ↓
Return order

ALL critical operations must be transactional.

If any critical operation fails:

- order must not be partially created
- stock must not be partially modified
- cart must remain recoverable

Do not create a fake payment success.

At this stage paymentStatus should remain something like:

PENDING

because PhonePe is not implemented yet.

- database constraint
- transaction behavior
