==================================================
STEP 2 — PRICING ARCHITECTURE
==================================================

The pricing pipeline should conceptually become:

PRODUCT PRICE
    ↓
VARIANT PRICE
    ↓
ITEM SUBTOTAL
    ↓
ELIGIBLE PRODUCT/CATEGORY DISCOUNTS
    ↓
CART SUBTOTAL
    ↓
COUPON DISCOUNT
    ↓
SHIPPING
    ↓
FINAL TOTAL

However:

Do NOT blindly implement this exact order if the existing business model requires another order.

The important requirement is:

THE SERVER MUST OWN THE FINAL CALCULATION.

The frontend must never determine the authoritative discount or final total.

==================================================
STEP 3 — MONEY SAFETY
==================================================

Use the existing Phase 2 money architecture.

Rules:

- Never use JavaScript floating-point arithmetic for authoritative money.
- Never trust client-supplied discount amount.
- Never trust client-supplied subtotal.
- Never trust client-supplied total.
- Store monetary values safely using the existing DECIMAL/integer-pa​​ise approach.
- Round deterministically.
- Use one centralized pricing/discount calculation mechanism.

Do not create multiple competing money helpers.

STEP 5 — PROMOTION TYPES
==================================================

Support these practical types:

1. COUPON

Requires a customer-entered code.

2. AUTOMATIC

Can apply automatically when eligibility conditions are satisfied.

3. PRODUCT_DISCOUNT

Applies to eligible products.

4. CATEGORY_DISCOUNT

Applies to eligible categories.

If implementing all four in one model creates unnecessary complexity, use a clean Promotion + PromotionRule architecture.

The architecture should allow future promotion types without rewriting Order.

==================================================
STEP 8 — COUPON CODE RULES
==================================================

Coupon codes must:

- be unique
- be normalized consistently
- be case-insensitive
- have safe length limits
- reject invalid characters where appropriate
- not contain accidental whitespace
- be validated server-side

Example:

SAVE10

save10

SaVe10

should resolve consistently if the business chooses case-insensitive codes.

Do not store multiple duplicate codes.

==================================================
STEP 9 — USAGE LIMITS
==================================================

Support:

GLOBAL USAGE LIMIT

Example:

First 1,000 customers.

PER CUSTOMER LIMIT

Example:

Each customer can use SAVE10 once.

The backend must enforce these limits atomically.

Do not rely only on:

"SELECT usageCount → check → increment"

because concurrent requests can bypass the limit.

Use appropriate database transaction/locking/atomic update behavior.

==================================================
STEP 10 — GUEST COUPON POLICY
==================================================

Choose and document a clear policy.

Recommended:

- Guests may apply public coupons if the coupon does not require customer-specific usage tracking.
- Coupons with per-customer usage restrictions require login.
- Once the customer logs in, usage eligibility is rechecked.

Do not allow guest users to bypass per-customer limits.

If you choose another policy, explain why.

==================================================
STEP 11 — PROMOTION PRIORITY
==================================================

Define deterministic promotion behavior.

Example:

Product/category automatic discount
↓
Coupon
↓
Final discount

However, do NOT allow arbitrary stacking by default.

Recommended initial rule:

ONE coupon/promotion code per order.

Avoid discount stacking unless explicitly supported.

If an automatic product/category promotion and coupon are both active, define clearly whether:

A. coupon replaces automatic promotion
B. automatic promotion applies first and coupon applies to remaining eligible subtotal
C. only the best discount applies

Choose the safest business rule.

Prefer predictable customer behavior and prevent accidental over-discounting.

Document the decision.

STEP 12 — DISCOUNT CALCULATION SERVICE
==================================================

Create ONE authoritative server-side pricing/discount calculation service.

Conceptually:

calculateCartPricing(cart, customer, couponCode)

It should return something like:

{
  items: [...],
  subtotal: ...,
  discount: ...,
  shipping: ...,
  grandTotal: ...,
  appliedPromotion: ...,
  messages: [...]
}

Use actual project types/structures rather than blindly copying this shape.

The same calculation logic must be used by:

- cart/checkout preview
- coupon application
- order creation

Do NOT calculate discounts separately in three places.

- promotion/coupon identifier if appropriate
- coupon code
- promotion name
- discount type
- discount value/rule

The exact database design can vary.

DO NOT make historical orders depend on the current Promotion row.

If an admin later edits/deletes a promotion, existing orders must still show their original discount correctly.

STEP 23 — CONCURRENCY
==================================================

Think carefully about:

Two customers applying the last available coupon usage at the same time.

Example:

usageLimit = 100

usageCount = 99

Two checkout requests arrive simultaneously.

The system must not allow usageCount to become 101.

Use database transactions/atomic operations consistent with the existing Sequelize architecture.

==================================================
STEP 24 — IDEMPOTENCY
==================================================

Existing Phase 2 order idempotency must remain intact.

If the same order creation request is retried:

- do not consume the coupon twice
- do not create two orders
- do not increment promotion usage twice

Promotion usage must be tied correctly to successful order creation.

IMPORTANT:

Do not permanently consume a coupon simply because a customer clicked "Apply".

Usage should be consumed according to the actual business event chosen by the architecture, normally successful order creation.

==================================================
STEP 25 — ORDER CANCELLATION
==================================================

Define what happens when a discounted order is cancelled.

Recommended:

Do NOT automatically restore global coupon usage unless the business explicitly requires it.

Document the rule.

If you decide to restore usage, make it transaction-safe and idempotent.

Do not accidentally create unlimited coupon reuse through cancellation/retry behavior.
